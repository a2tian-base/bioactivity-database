# Migration proposal: from a hERG IC50 database to a general endpoint-driven bioactivity system

## Goal of the migration

The goal is to generalize the current hERG IC50 database into a system that can ingest, normalize, store, and export bioactivity data for arbitrary user-selected endpoints.

Today, the repository is explicitly organized around hERG IC50. The README describes it as a SQL-first application for storing, enriching, and browsing hERG IC50 measurements, with PostgreSQL as the canonical data model, Streamlit as the UI, and Python scripts for ChEMBL, PubChem, UniChem, identifier, and structure enrichment workflows. It also states that `ic50_um`, `pic50`, and `pic50_qualifier` are generated by PostgreSQL rather than application code. [1]

The migration should preserve the current strengths of the system: compound deduplication, source provenance, raw source payload retention, automatic ingestion, and normalized result browsing. It should remove the assumption that every stored result is a hERG IC50 measurement.

The target system should support endpoints such as:

```text
hERG IC50
CYP3A4 IC50
DRD2 Ki
EGFR EC50
hERG percent inhibition
Ames assay outcome
solubility
permeability
other source-defined bioactivity endpoints
```

The key design decision is to make the database **endpoint-driven** rather than **hERG-driven**.

An endpoint is the saved definition of the biological question the user wants to answer. For example, “hERG IC50” is not merely a text label. It means a target, a measurement type, normalization rules, inclusion criteria, and source-specific query parameters.

## Problem the migration solves

The current system works well for one endpoint, but several parts of the design are hard-coded around IC50.

The main result table is `ic50_results`. It stores `ic50_value`, restricts units to `pM`, `nM`, `uM`, and `mM`, stores a one-character qualifier, derives `ic50_um`, derives `pic50`, derives `pic50_qualifier`, and enforces uniqueness on `(source_record_id, endpoint)`. [2] This is appropriate for hERG IC50, but it does not generalize cleanly to Ki, EC50, percent inhibition, categorical activity outcomes, solubility, permeability, or other non-IC50 endpoints.

The Python ingestion pipeline is already adapter-oriented, but its validation layer is still IC50-specific. The pipeline imports `ALLOWED_IC50_UNITS` and `ALLOWED_QUALIFIERS`, defines a `SourceAdapter` interface with `iter_raw_rows`, `enrich_batch`, and `map_row`, and validates records as IC50 measurements. [3]

The ChEMBL adapter is parameterized, but the parameters are currently endpoint-like arguments to a hERG-specific ingestion path: `target_chembl_id`, `standard_type`, and `relations`. It then queries ChEMBL activities using those values. [4] The PubChem adapter similarly takes `target_gene_symbol`, `target_gene_id`, and `activity_name_regex`, then filters rows by target gene ID, activity name, and `Activity Value [uM]`. [5]

The UI is also IC50-specific. It sets the page title to “hERG IC50 Database” and exposes tabs such as “Add IC50 Result,” “Upload CSV,” “Browse Results,” and “Dashboard.” [6]

The migration solves four problems:

First, it removes IC50 as a structural assumption. IC50 becomes one measurement type, not the shape of the whole result table.

Second, it makes endpoint definitions durable. A result should point to a saved endpoint definition, not merely to a free-text value such as `"IC50"`.

Third, it keeps source ingestion reproducible. The system should store not only normalized measurements, but also the exact source query configuration and run summary used to obtain them.

Fourth, it avoids over-modeling. Instead of creating many target, assay, measurement ontology, and endpoint-source tables immediately, the first generalized version should use a small number of tables with JSON specifications where flexibility is more valuable than relational normalization.

## Design principle

The simplified model should preserve only facts that the system cannot safely derive later.

The required facts are:

```text
What molecule is this?
What external identifier resolved it?
What source record did this come from?
What endpoint was the user trying to collect?
What normalized result was extracted?
When was the ingestion run, with what query, and what happened?
```

That leads to six required physical tables:

```text
compounds
compound_identifiers
source_records
endpoints
bioactivity_results
ingestion_runs
```

The following existing tables can be retained but should not be treated as core to the generalized model:

```text
compound_names
compound_structure_assertions
compound_identifier_sources
```

They are useful support tables, but they are not required to generalize from hERG IC50 to arbitrary endpoints.

The design principle is therefore:

```text
Persist identity, provenance, endpoint definition, normalized results, and run history.
Keep source-specific and endpoint-specific variability in validated JSON configs and Python validation code.
Do not introduce relational catalog tables until the product actually needs global endpoint discovery or ontology management.
```

## End-user flow

The end user should experience the system as an endpoint-selection and ingestion workflow.

A typical flow should be:

```text
1. User creates or selects an endpoint.

2. The system asks for the minimum endpoint definition:
   target or assay
   measurement type
   canonical unit or value kind
   selected sources
   source-specific query parameters

3. The system previews external records from the selected sources.

4. The user saves the endpoint.

5. The system stores:
   one endpoints row
   source-specific configs inside endpoints.source_configs

6. The user runs ingestion.

7. The system stores:
   source_records
   bioactivity_results
   ingestion_runs summary

8. The user browses, filters, exports, or dashboards the endpoint-specific results.
```

For hERG IC50, the user-facing flow would be:

```text
User searches or creates endpoint:
  hERG IC50

System defines endpoint:
  target = hERG / KCNH2 / Homo sapiens
  measurement type = IC50
  value kind = concentration
  canonical unit = uM
  p-value name = pIC50

System defines source configs:
  ChEMBL:
    target_chembl_id = CHEMBL240
    standard_type = IC50
    accepted relations = =, <, >

  PubChem:
    target_gene_symbol = KCNH2
    target_gene_id = 3757
    activity_name_regex = IC50

User previews source rows.

User runs ingestion.

System writes normalized bioactivity results.
```

The same flow should later support a second endpoint, such as CYP3A4 IC50, by changing the endpoint row and source configs, not by creating a new table, new hard-coded script, or new endpoint-specific schema.

## Proposed data model

The proposed data model has six required tables.

```text
compounds
compound_identifiers
source_records
endpoints
bioactivity_results
ingestion_runs
```

The existing `compound_names`, `compound_structure_assertions`, and `compound_identifier_sources` tables may remain in the database, but they should be considered optional support tables rather than central migration concepts.

### 1. `compounds`

Purpose: stores the internal molecule entity.

Each row represents one deduplicated compound known to the system.

The current schema already uses this pattern. The `compounds` table stores `compound_id`, `canonical_smiles`, `standard_inchi`, `standard_inchikey`, and timestamps. It also defines a unique index on normalized `standard_inchikey` when present. [2]

Intended fields:

```text
compound_id
canonical_smiles
standard_inchi
standard_inchikey
created_at
updated_at
```

Why it exists: every bioactivity result needs to attach to a stable internal compound. Results should not point directly to PubChem CIDs, ChEMBL IDs, names, or raw source-specific compound records.

Example:

```text
compound_id: 42
canonical_smiles: CC(=O)OC1=CC=CC=C1C(=O)O
standard_inchikey: BSYNRYMUTXBXSQ-UHFFFAOYSA-N
```

### 2. `compound_identifiers`

Purpose: stores external database identifiers for compounds.

Each row means:

```text
This external identifier refers to this internal compound.
```

The current table stores a `namespace`, an `identifier_value`, a generated normalized identifier value, and an `is_primary` flag. It enforces uniqueness on `(namespace, normalized_value)` and allows one primary identifier per compound per namespace. [2]

Intended fields:

```text
compound_identifier_id
compound_id
namespace
identifier_value
normalized_value
is_primary
created_at
updated_at
```

Example rows:

```text
compound_id | namespace    | identifier_value
42          | pubchem_cid  | 2244
42          | chembl_id    | CHEMBL25
42          | unii         | R16CO5Y76E
```

Why it exists: external identifiers are one-to-many. A single compound can have a PubChem CID, ChEMBL ID, UNII, CAS number, internal ID, vendor ID, and future source-specific identifiers. Keeping identifiers in their own table avoids adding new provider-specific columns to `compounds`.

This table also protects deduplication. The database can enforce that one normalized PubChem CID or ChEMBL ID does not silently map to multiple internal compounds.

### 3. `source_records`

Purpose: stores raw external provenance.

Each row represents one external record pulled from a source.

The current schema stores `source_name`, `source_record_key`, `record_type`, `source_release`, `source_url`, and `raw_payload`, with a uniqueness constraint on `(source_name, source_record_key)`. [2]

Intended fields:

```text
source_record_id
source_name
source_record_key
record_type
source_release
source_url
raw_payload
created_at
updated_at
```

Example ChEMBL source record:

```text
source_name: chembl
source_record_key: activity:CHEMBL_ACTIVITY_123456
record_type: activity
source_release: ChEMBL_35
raw_payload: { full ChEMBL activity JSON }
```

Example PubChem source record:

```text
source_name: pubchem
source_record_key: aid:1234/sid:5678/cid:2244/activity:IC50
record_type: bioactivity_row
raw_payload: { full PubChem concise assay row }
```

Why it exists: this is the provenance boundary. `source_records` stores what the external source said. `bioactivity_results` stores what this system extracted and normalized from that source record.

Those should not be merged. One raw source record may produce multiple normalized measurements, or it may need to be reinterpreted later after parser changes. Keeping raw provenance separate makes the normalized data auditable.

### 4. `endpoints`

Purpose: stores the user’s saved endpoint definition.

Each row represents one endpoint that the system can ingest.

This is the key new table.

A simplified schema:

```sql
CREATE TABLE endpoints (
    endpoint_id BIGSERIAL PRIMARY KEY,
    endpoint_key TEXT NOT NULL UNIQUE,
    display_name TEXT NOT NULL,

    spec JSONB NOT NULL,
    source_configs JSONB NOT NULL DEFAULT '{}'::JSONB,

    spec_hash TEXT NOT NULL UNIQUE,
    active BOOLEAN NOT NULL DEFAULT TRUE,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

The `spec` field stores the endpoint’s scientific meaning. The `source_configs` field stores source-specific query plans.

Example endpoint:

```json
{
  "endpoint_key": "herg_ic50",
  "display_name": "hERG IC50",
  "spec": {
    "target": {
      "preferred_name": "hERG",
      "gene_symbol": "KCNH2",
      "organism": "Homo sapiens",
      "identifiers": {
        "chembl_target_id": "CHEMBL240",
        "ncbi_gene_id": "3757"
      }
    },
    "measurement": {
      "type": "IC50",
      "value_kind": "concentration",
      "canonical_unit": "uM",
      "supports_p_value": true,
      "p_value_name": "pIC50"
    },
    "normalization": {
      "allowed_units": ["pM", "nM", "uM", "mM"],
      "allowed_relations": ["=", "<", ">"]
    },
    "inclusion_criteria": {
      "organism": "Homo sapiens",
      "direct_target_only": true
    }
  },
  "source_configs": {
    "chembl": {
      "target_chembl_id": "CHEMBL240",
      "standard_type": "IC50",
      "standard_relation__in": ["=", "<", ">"],
      "data_validity_comment__isnull": true
    },
    "pubchem": {
      "target_gene_symbol": "KCNH2",
      "target_gene_id": "3757",
      "activity_name_regex": "(?i)\\bIC50\\b"
    }
  }
}
```

Why it exists: the result table needs to point to a durable endpoint definition. Without this table, results would have only a loose text label such as `"IC50"` or `"hERG IC50"`, which is not enough to reconstruct what was queried or why a source row was included.

Why `source_configs` lives in `endpoints`: this is the simplest robust version. A separate `endpoint_sources` table is not necessary yet. Source configs can be promoted to their own table later if the system needs per-source versioning, per-source enable/disable state, source-level ownership, or complex source management.

### 5. `bioactivity_results`

Purpose: stores normalized measurements extracted from source records.

This table replaces `ic50_results`.

A simplified schema:

```sql
CREATE TABLE bioactivity_results (
    result_id BIGSERIAL PRIMARY KEY,

    endpoint_id BIGINT NOT NULL REFERENCES endpoints(endpoint_id),
    compound_id BIGINT NOT NULL REFERENCES compounds(compound_id),
    source_record_id BIGINT NOT NULL REFERENCES source_records(source_record_id),
    ingestion_run_id BIGINT,

    result_key TEXT NOT NULL,

    measurement_type TEXT NOT NULL,
    value_kind TEXT NOT NULL CHECK (
        value_kind IN ('concentration', 'percent', 'numeric', 'categorical', 'text')
    ),

    original_value NUMERIC,
    original_unit TEXT,
    original_relation TEXT,

    standard_value NUMERIC,
    standard_unit TEXT,
    standard_relation TEXT,

    p_value NUMERIC,
    p_value_relation TEXT,

    value_text TEXT,

    assay_context JSONB NOT NULL DEFAULT '{}'::JSONB,
    quality_flags JSONB NOT NULL DEFAULT '{}'::JSONB,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    UNIQUE (endpoint_id, source_record_id, result_key)
);
```

Example hERG IC50 result:

```text
endpoint_id: herg_ic50
compound_id: 42
source_record_id: ChEMBL activity record
measurement_type: IC50
value_kind: concentration
original_value: 50
original_unit: nM
original_relation: =
standard_value: 0.05
standard_unit: uM
standard_relation: =
p_value: 7.3010
p_value_relation: =
```

Example percent inhibition result:

```text
measurement_type: inhibition
value_kind: percent
original_value: 72
original_unit: %
standard_value: 72
standard_unit: %
p_value: NULL
value_text: NULL
```

Example categorical result:

```text
measurement_type: activity_outcome
value_kind: categorical
standard_value: NULL
standard_unit: NULL
p_value: NULL
value_text: active
```

Why it exists: this is the core output of the system. It stores normalized measurements in a form that can represent IC50, Ki, EC50, percent inhibition, categorical outcomes, and future endpoint types.

Why it should not be merged with `source_records`: `source_records` stores raw external evidence. `bioactivity_results` stores the system’s interpretation of that evidence. Keeping those separate is what allows reprocessing, auditing, and parser improvements without losing the original source record.

Why `result_key` exists: one source record may produce more than one normalized result. The source adapter should generate a stable key that identifies the specific extracted measurement. For ChEMBL this may be based on an activity ID; for PubChem it may be based on AID, SID, CID, activity name, and value field.

### 6. `ingestion_runs`

Purpose: stores execution history, reproducibility metadata, and quality-control summaries.

Each row means:

```text
The system attempted to ingest one endpoint from one source using this query configuration.
```

A simplified schema:

```sql
CREATE TABLE ingestion_runs (
    ingestion_run_id BIGSERIAL PRIMARY KEY,

    endpoint_id BIGINT NOT NULL REFERENCES endpoints(endpoint_id),

    source_name TEXT NOT NULL,
    source_release TEXT,

    query_config JSONB NOT NULL DEFAULT '{}'::JSONB,
    query_hash TEXT NOT NULL,

    status TEXT NOT NULL CHECK (
        status IN ('running', 'succeeded', 'failed', 'partial')
    ),

    started_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    finished_at TIMESTAMPTZ,

    rows_seen INTEGER NOT NULL DEFAULT 0,
    rows_inserted INTEGER NOT NULL DEFAULT 0,
    rows_updated INTEGER NOT NULL DEFAULT 0,
    rows_skipped INTEGER NOT NULL DEFAULT 0,
    rows_failed INTEGER NOT NULL DEFAULT 0,

    qc_summary JSONB NOT NULL DEFAULT '{}'::JSONB,
    error_summary JSONB NOT NULL DEFAULT '{}'::JSONB
);
```

Example:

```text
endpoint_id: herg_ic50
source_name: chembl
source_release: ChEMBL_35
query_config:
  target_chembl_id: CHEMBL240
  standard_type: IC50
  standard_relation__in: ["=", "<", ">"]
status: succeeded
rows_seen: 2500
rows_inserted: 2100
rows_skipped: 300
rows_failed: 100
qc_summary:
  invalid_units: 12
  missing_compound_identity: 44
  duplicate_source_records: 81
```

Why it exists: automatic ingestion is operational. Users will rerun the same endpoint, change endpoint definitions, update source configs, fix parsers, and compare outputs across source releases. Without an `ingestion_runs` table, the system cannot reliably answer:

```text
When was this endpoint last ingested?
Which source was used?
Which exact query config was used?
How many rows were skipped?
Which rows came from the latest run?
Did this run partially fail?
```

This table is essential for reproducibility.

## Optional and deferred tables

The current schema includes additional compound-related tables. They can remain in the database, but they do not need to be central to the migration.

### `compound_names`

Purpose: stores display names, aliases, normalized names, and preferred-name status.

The current table stores `name`, generated `normalized_name`, `name_type`, and `is_preferred`, and it enforces uniqueness of normalized names per compound and one preferred name per compound. [2]

Recommendation: keep if the UI needs compound-name search or display. Defer or treat as support if the first generalized system is focused on ingestion and export.

It should not be used for compound deduplication. Names are aliases, not reliable identifiers.

### `compound_structure_assertions`

Purpose: stores source-specific structural claims linked to a source record.

The current table links `compound_id` and `source_record_id`, then stores source-asserted `canonical_smiles`, `standard_inchi`, and `standard_inchikey`, with uniqueness on `(compound_id, source_record_id)`. [2]

Recommendation: keep if structural provenance and source conflict detection matter. Defer if the generalized MVP only needs one canonical structure per compound.

This table is scientifically useful, but it is not necessary to generalize from hERG IC50 to arbitrary endpoints.

### `compound_identifier_sources`

Purpose: links compound identifiers to the source records that asserted them.

The current schema links `compound_identifier_id` to `source_record_id` and enforces uniqueness on that pair. [2]

Recommendation: defer as a core concept. The system already preserves raw source payloads in `source_records`, so identifier-level provenance is useful but not required for the endpoint migration.

## Why this model is simpler than the previous proposal

The earlier model included tables such as:

```text
target_entities
target_identifiers
source_targets
source_assays
source_measurement_availability
measurement_types
endpoint_templates
endpoint_sources
```

Those tables may eventually be useful, but they are not necessary for the first robust generalized system.

The simplified model moves those concerns into three places:

```text
Endpoint definition:
  endpoints.spec JSONB

Source-specific query configuration:
  endpoints.source_configs JSONB

Validation and normalization:
  Python models and adapter-specific validators
```

For example, instead of a `measurement_types` table, the endpoint validator can enforce rules in code:

```text
If value_kind = concentration:
  canonical_unit is required.
  p_value may be computed if supports_p_value = true.

If value_kind = percent:
  canonical_unit should be "%".
  p_value must be null.

If value_kind = categorical:
  value_text is required.
  numeric standard_value may be null.
```

Instead of a `target_entities` table, the endpoint stores a snapshot of target identity:

```json
{
  "preferred_name": "hERG",
  "gene_symbol": "KCNH2",
  "organism": "Homo sapiens",
  "identifiers": {
    "chembl_target_id": "CHEMBL240",
    "ncbi_gene_id": "3757"
  }
}
```

This duplicates target metadata across endpoints, but that is acceptable at this stage. The endpoint row is a saved scientific definition, and the snapshot records what the user meant at the time the endpoint was created.

The design intentionally avoids building a local source catalog. The system can query ChEMBL and PubChem live during endpoint preview, then persist only the user’s selected endpoint and source configs.

## What stays in application code

The database should store validated endpoint specs, source configs, normalized results, raw source records, and run history. It should not encode every validation rule relationally.

The following should live in Python initially:

```text
endpoint template registry
endpoint spec validation
source config validation
unit normalization
qualifier normalization
p-value computation
source-specific row filtering
source-specific result_key generation
preview logic
```

Example code-level endpoint templates:

```text
target_concentration_potency
target_percent_activity
assay_outcome
admet_numeric_property
```

These do not need SQL tables yet. A small in-code registry is easier to reason about and test.

## Proposed migration plan

### Phase 0: Establish hERG IC50 as the regression baseline

Before changing the schema, freeze the current behavior.

Capture fixtures for:

```text
manual IC50 entry
CSV IC50 upload
ChEMBL hERG IC50 ingestion
PubChem hERG IC50 ingestion
compound registration
source record upsert
IC50 normalization to µM
pIC50 derivation
qualifier inversion
```

The migration should be considered safe only if hERG IC50 can be reproduced through the new generalized path.

### Phase 1: Add the new generic tables

Add:

```text
endpoints
bioactivity_results
ingestion_runs
```

Keep existing tables:

```text
compounds
compound_identifiers
source_records
ic50_results
compound_names
compound_structure_assertions
compound_identifier_sources
```

Do not drop anything initially.

Seed one endpoint:

```text
endpoint_key = herg_ic50
display_name = hERG IC50
```

Store ChEMBL and PubChem configs inside `endpoints.source_configs`.

### Phase 2: Introduce a generic measurement object

Replace the IC50-specific internal object with a generic measurement object.

Current conceptual object:

```text
Ic50Input
  ic50_value
  ic50_unit
  qualifier
```

New conceptual object:

```text
MeasurementInput
  measurement_type
  value_kind

  original_value
  original_unit
  original_relation

  standard_value
  standard_unit
  standard_relation

  p_value
  p_value_relation

  value_text

  assay_context
  quality_flags
  result_key
```

For hERG IC50, this object still stores the same scientific information. It just no longer assumes IC50 is the only possible result type.

### Phase 3: Add `upsert_bioactivity_result`

Create a generic upsert function or application-level write path for `bioactivity_results`.

The new write path should require:

```text
endpoint_id
compound_id
source_record_id
result_key
measurement_type
value_kind
normalized measurement fields
assay_context
quality_flags
ingestion_run_id
```

Keep `upsert_ic50_result` temporarily as a compatibility wrapper if needed.

### Phase 4: Write hERG IC50 into `bioactivity_results`

Modify the existing hERG ChEMBL and PubChem ingestion paths so that they write to `bioactivity_results`.

During this phase, there are two acceptable strategies:

```text
Option A:
  Write to both ic50_results and bioactivity_results temporarily.

Option B:
  Write only to bioactivity_results and create an ic50_results compatibility view.
```

Option B is cleaner once downstream code is ready.

A compatibility view could expose hERG IC50 rows in the old shape:

```sql
CREATE VIEW ic50_results_compat_v AS
SELECT
    r.result_id,
    r.compound_id,
    r.source_record_id,
    e.endpoint_key AS endpoint,
    r.original_value AS ic50_value,
    r.original_unit AS ic50_unit,
    r.original_relation AS qualifier,
    r.standard_value AS ic50_um,
    r.p_value AS pic50,
    r.p_value_relation AS pic50_qualifier,
    r.created_at,
    r.updated_at
FROM bioactivity_results r
JOIN endpoints e ON e.endpoint_id = r.endpoint_id
WHERE r.measurement_type = 'IC50'
  AND r.value_kind = 'concentration';
```

### Phase 5: Refactor source adapters to read endpoint configs

The ChEMBL adapter should stop receiving hERG-specific parameters directly from a hERG script. Instead, it should receive the selected endpoint and the ChEMBL config from `endpoints.source_configs`.

Current conceptual form:

```python
ChemblAdapter(
    target_chembl_id="CHEMBL240",
    standard_type="IC50",
    relations="=,<,>"
)
```

New conceptual form:

```python
endpoint = load_endpoint("herg_ic50")
chembl_config = endpoint.source_configs["chembl"]

ChemblAdapter(
    endpoint=endpoint,
    source_config=chembl_config
)
```

The PubChem adapter should follow the same pattern.

Current conceptual form:

```python
PubChemAdapter(
    target_gene_symbol="KCNH2",
    target_gene_id="3757",
    activity_name_regex="(?i)\\bIC50\\b"
)
```

New conceptual form:

```python
endpoint = load_endpoint("herg_ic50")
pubchem_config = endpoint.source_configs["pubchem"]

PubChemAdapter(
    endpoint=endpoint,
    source_config=pubchem_config
)
```

This phase is mostly about moving parameters from code into endpoint configuration.

### Phase 6: Add endpoint preview

Add a preview command before full ingestion.

Example:

```bash
python -m app.bioactivity.preview \
  --endpoint herg_ic50 \
  --source chembl \
  --limit 20
```

Preview should show:

```text
example source rows
observed units
observed relations
rows that would be skipped
skip reasons
missing compound identifiers
target mismatch warnings
measurement mismatch warnings
```

Do not create source catalog tables yet. Preview can query the external source live using the selected endpoint’s source config.

### Phase 7: Update the UI

Refactor the Streamlit UI from IC50-specific language to endpoint-aware language.

Replace:

```text
hERG IC50 Database
Add IC50 Result
```

with:

```text
Bioactivity Database
Add Measurement
```

The manual-entry form should change based on the selected endpoint:

```text
Concentration endpoint:
  value
  unit
  relation

Percent endpoint:
  percent value
  relation

Categorical endpoint:
  outcome text
```

The browse and dashboard tabs should filter by `endpoint_id`.

### Phase 8: Add a second endpoint without schema changes

This is the forcing function.

Add a second endpoint such as:

```text
CYP3A4 IC50
DRD2 Ki
EGFR IC50
hERG percent inhibition
```

The second endpoint should require only:

```text
one new endpoints row
new source_configs JSON
possibly minor adapter mapping logic
no new result table
no new endpoint-specific script
no schema migration
```

If this works, the migration has achieved its purpose.

### Phase 9: Deprecate IC50-specific paths

After hERG IC50 works through the generic path and at least one second endpoint has been ingested, deprecate IC50-specific tables and functions.

Recommended sequence:

```text
1. Keep old hERG ingestion scripts as wrappers around the generic endpoint ingestion command.

2. Keep ic50_results as a table or compatibility view while the UI is migrated.

3. Update read paths to use bioactivity_results.

4. Update CSV import/export to be endpoint-aware.

5. Stop direct writes to ic50_results.

6. Drop ic50_results only after no application code depends on it.
```

## Acceptance criteria

The migration is successful when the following are true:

```text
1. hERG IC50 ingestion still works.

2. hERG IC50 data can be represented in bioactivity_results.

3. Source records remain traceable through source_records.

4. Every result points to a saved endpoint.

5. Every ingestion run records source name, source release if available,
   query config, status, row counts, and QC summary.

6. ChEMBL and PubChem adapters read endpoint-specific configs instead of
   hard-coded hERG parameters.

7. The UI can select an endpoint before browsing, manual entry, upload, or export.

8. A second endpoint can be added without creating a new result table.

9. Non-IC50 measurements can be represented without schema changes.

10. Optional support tables such as compound_names and compound_structure_assertions
    remain useful but are not required to understand the core model.
```

## Summary recommendation

The generalized system should use the smallest robust schema:

```text
compounds
compound_identifiers
source_records
endpoints
bioactivity_results
ingestion_runs
```

Each table has a tight justification:

```text
compounds:
  one internal molecule entity

compound_identifiers:
  external IDs for compound resolution and deduplication

source_records:
  raw external provenance

endpoints:
  saved scientific question plus source-specific query configs

bioactivity_results:
  normalized extracted measurements

ingestion_runs:
  reproducibility, execution history, and QC
```

The migration should not introduce a full target catalog, assay catalog, measurement ontology, source availability cache, or endpoint-source table yet. Those can be added later if the system needs global endpoint discovery or heavier administrative control.

The immediate objective is narrower and clearer: preserve the current hERG IC50 workflow while replacing the IC50-specific result model with a generic endpoint-driven result model.
